# Authopus — v0.1.0 Release Scope

**Status:** Approved scope baseline (A01)  
**Decision date:** November 2, 2026  
**Alpha:** December 31, 2026 — `v0.1.0-alpha.1`  
**Public:** January 31, 2027 — `v0.1.0`  

## 1. Objective

Release a usable, open-source, single-organization AI agent authorization platform that demonstrates: **Which agent took what action under whose authority on behalf of whom?**

The initial supported end-to-end path is an authenticated agent making an MCP **tool call** through an Authopus enforcement gateway. Authopus validates trusted identity and delegated authority, evaluates a versioned policy, enforces allow/deny/approval-required outcomes, and records auditable evidence. The release does not claim to prevent bypass when traffic avoids the configured enforcement point.

## 2. Release strategy

Alpha and public `v0.1.0` have **the same feature scope**. All required features must be demonstrably working by the alpha deadline. January adds no planned features: it is reserved for fixing defects, security and reliability hardening, tests, usability improvements, documentation, and repeatable release artifacts.

`v0.1.0` is an **experimental public release**, not a production-readiness or stable-API promise. Incompatible changes in subsequent `0.x` versions are possible and must be documented.

## 3. In scope — required capabilities

| Area | Required release capability |
| --- | --- |
| Architecture | One Go service with five internally separated concerns; no microservices. |
| Authentication | OIDC validation for agent/integration identity using configured trusted issuers; reject invalid, expired, forged, or inappropriate tokens. |
| Identity and delegation | Distinguish authenticated caller, agent, represented principal, delegated authority, action, resource, and trusted context. Never assume the agent inherits all user permissions. |
| Authorization API | REST interface accepting typed authorization requests and returning distinct allow, deny, approval-required, and error outcomes with explainable reasons. |
| Native policy engine | Authopus-owned Go evaluator; default deny; explicit deny overrides allow; deterministic, bounded, typed evaluation; explainable decisions. No OPA or third-party policy execution engine. |
| Policy-as-code | Versioned YAML policies from Git with validation, polling, activation, retention of last valid configuration, and rollback. Invalid updates must not activate. |
| Enforcement | **MCP gateway only** as a shipping integration, covering **MCP tool calls only**. A small internal enforcement interface permits later adapters but no additional integration ships in v0.1.0. |
| Failure behavior | Fail closed on missing authorization, invalid identity, authorization-service failures, timeouts, malformed responses, or unapproved actions. A policy denial is distinct from a system error. |
| Human approval | Approval-required actions are blocked pending an authorized human decision. Provide **REST API and CLI** for listing/reviewing, approving, and rejecting requests. Support expiry and revalidation before execution. No web approval UI. |
| Audit | PostgreSQL-backed records connecting identity, principal/delegation, action, resource, policy version, decision, reason, and observed enforcement/execution outcome. Do not conflate authorization with confirmed downstream execution. |
| Observability | Structured logs, request correlation, health endpoints, basic Prometheus-compatible metrics, and basic OpenTelemetry tracing without secret leakage. |
| Local deployment | Single-organization Docker Compose deployment with PostgreSQL, documented configuration, migrations, and reproducible startup. Include organization identifiers where needed for future evolution, without multi-tenant behavior. |
| Developer experience | Runnable MCP demo, documented REST API, policy examples, CLI for approval workflow and basic platform exercises, tests, and clean-clone quickstart. |
| Open source | Public source, license, security reporting policy, contribution instructions, release notes, tagged release and reproducible artifacts. |

## 4. Explicitly out of scope

- MCP resources and prompts; the gateway protects **tool calls only**.
- Additional enforcement adapters, general-purpose HTTP middleware, and a supported Go SDK.
- Approval dashboard or other substantial web UI.
- Multi-tenant isolation, multi-region deployment, Kubernetes, and high availability.
- gRPC, advanced analytics, enterprise integrations, and broad identity-provider support beyond the chosen OIDC contract.
- Building an identity provider, secret manager, agent runtime, or general-purpose model gateway.
- Universal OAuth/token exchange support for arbitrary upstream MCP servers.
- Enforcement against agents that bypass the configured gateway or supported integration point.
- General prompt-injection detection, content guardrails, sandboxing, and full LLM security coverage.
- Billing, monetization, commercial hosting, and production-readiness certification.
- A general policy language, third-party evaluator, or automatic policy-schema migration framework.

## 5. Alpha release gate — December 31, 2026

All checks below are mandatory:

1. A real agent/client can invoke a supported MCP tool through the Authopus gateway and a real upstream MCP server.
2. OIDC identity and delegation context are validated; forged, expired, missing, or unauthorized claims are rejected.
3. The native policy engine correctly demonstrates allow, explicit deny, default deny, and approval-required paths, with an understandable explanation.
4. Approved tool calls are forwarded; denied, pending, rejected, expired, and error-path calls do not reach the upstream tool.
5. Approval requests can be inspected and decided through REST and CLI, with expiry and authorization revalidation before execution.
6. Git-backed YAML policies validate, activate, reject invalid updates, preserve the previous valid state, and roll back.
7. Audit records link agent, represented principal, authority, requested action/resource, policy/decision, and observed outcome without leaking secrets.
8. Automated unit, integration, and negative security tests pass; no known critical authorization bypass remains open.
9. A clean Docker Compose setup runs the end-to-end demonstration using documented steps.
10. `v0.1.0-alpha.1` has a tag, build artifacts, basic quickstart, test evidence, and known limitations.

**Alpha go/no-go:** Any failed mandatory check blocks the alpha release. Reduce nonessential implementation breadth, not security invariants, to recover schedule.

## 6. Public release gate — January 31, 2027

All alpha gates continue to pass against the final release candidate, plus:

1. Release-blocking defects and known critical/high-risk security issues are fixed or explicitly prevent release; regression tests cover fixes.
2. Authentication, delegation, approval lifecycle, audit integrity, input validation, failure handling, restart, concurrency, and migration scenarios have documented test evidence.
3. Basic latency/resource benchmarks and operational limits are documented; no unsupported performance claims are made.
4. A new developer can reproduce installation, configuration, policies, MCP integration, approval, and audit inspection from a clean clone.
5. README, architecture overview, API reference, policy guide, threat boundaries, security limitations, and troubleshooting are consistent with the shipped build.
6. Open-source license, contribution guide, code of conduct, security reporting process, and issue templates are present; repository and artifacts pass secret scans.
7. Tagged `v0.1.0` source, container artifact, release notes, compatibility/experimental-status statement, and smoke-test evidence are published.
8. Feedback and issue-reporting paths are open.

**Public go/no-go:** Do not release while any mandatory gate fails. Do not describe the release as production-ready.

## 7. Constraints and implementation decisions deferred to other tasks

These do not reopen release scope unless they materially change the agreed scope:

- Exact names and responsibilities of the five internal modules.
- REST schemas, canonical policy `apiVersion`, and version compatibility.
- OIDC claims, trusted issuers, and precise delegation proof.
- Initial operator set, unknown/null semantics, evaluation limits.
- Git polling, atomic activation, and rollback mechanism.
- MCP transport/version support and gateway protocol details.
- Approval persistence, expiration, revalidation, and CLI syntax.
- Audit schema, retention, and observable downstream outcomes.
- Telemetry details and measurable performance targets.
- Open-source license choice and repository governance.
